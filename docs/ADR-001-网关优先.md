# ADR-001：把网关提到终端之前

- 状态：已采纳（接手后的第一项决定）
- 日期：2026-11-10
- 决策人：巫伟鑫（发起人）+ 接手方

## 背景

计划书 5.1 的阶段顺序是：底座对标（30–45 人天）→ 重构（15–25）→ 网关与审查（25–35）→ 实验快照（15–20）。

按此顺序，产品**唯一不可替代的差异化**（本地网关、私钥代签、入口审查）要到第 20 周才第一次被验证。
若届时失败，前 12 周产出的 MobaXterm 替代品没有任何商业价值——它只是在红海里多做一个终端。

## 决策

先做 **豆 Gateway**（不含自有终端的代理接入层），终端形态作为第二阶段。

网关形态交付：MCP 回环服务 + 三档策略 + 审计，配一个极简审计面板。
不包含终端渲染、SFTP 文件树、内置编辑器。

## 理由

1. **成本结构**：终端渲染、SFTP 界面、编辑器、多标签约占 60% 工作量、0% 差异化，且用户已有可替代品（MobaXterm / Tabby / VS Code 终端）。
2. **获客话术更短**：从"换掉你的终端"变成"不用换终端，给现有终端加一层受控通道"，接入阻力低一个量级。
3. **验证周期**：8–10 周可交付可验证物，而非 20 周。
4. **失败成本**：若网关路线不成立，损失 2 个月而不是 6 个月。

## 代价

- 失去"单文件一站式终端"的差异化卖点，落在与 Tabby、Warp 同层的竞争里。
- 依赖用户已有可用的终端，纯新手用户（没装过任何 SSH 客户端）不在首发客群内。
- 后期把终端补进来时，会话对象与事件总线要能承载两套形态，架构不能只按网关设计。

## 后果与本轮落地

- 建立 `crates/dou-gateway`，先实现协议层与策略层，暂不引入 Tauri 外壳。
- 用 `tools/mcp_probe.py` 代替人工点验，每次改动都跑一遍九项自检。
- 阶段一"对标 MobaXterm"降级为**第二阶段的最小集**：连会话、传文件、接管 tmux 三件事。
- 若网关验证失败（MCP 客户端不支持、或代签不可行），回到终端路线并重估立项依据。
